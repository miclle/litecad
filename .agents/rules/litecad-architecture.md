# LiteCAD Architecture Rules

These rules keep LiteCAD product work aligned with the small Go + React single-binary architecture inherited from Goblet.

## Principles

- Preserve the existing `Handler -> Service -> Entity` layering.
- Keep route registration centralized in `internal/handler/handler.go`.
- Keep database connection and migration setup in `internal/database/`.
- Put GORM persistence models in `internal/entity/`; do not expose entities directly as HTTP contracts.
- Put reusable, business-agnostic helpers in `pkg/`, with small APIs and tests.
- Keep product capability claims grounded in shipped code, tests, and UI flows.

## Backend Boundaries

- Handlers own HTTP binding, status codes, response DTOs, cookies, and route grouping.
- Project handlers are split by domain: `project.go` owns project metadata, `project_models.go` owns thumbnail/model/source/preview/geometry delivery, `project_model_revisions.go` owns immutable model revision list/detail/restore routes, `project_cad.go` owns editable CAD document and History commands, `project_agent.go` owns advisory chat and parametric runs, `project_parametric.go` owns generated parametric artifact CRUD/save/parameter routes, and `project_errors.go` owns shared session/error translation.
- Application handlers use `pkg/httperr` for HTTP-status-aware errors. The website asset handlers use Fox's `httperrors` only for framework-level API/SPAs NotFound behavior.
- Services own business logic, validation that is not purely HTTP binding, and database access.
- Entities own GORM models, table names, persistence constants, and narrow model helpers.
- Configuration should stay bootstrap-focused: listen address, database driver, DSN, optional server-side AI provider settings, and similarly necessary startup settings.
- PostgreSQL and MySQL support must stay explicit for runtime. Tests may use SQLite directly through GORM helpers without adding SQLite as a runtime config option.
- Session-scoped resources must query by owner/session scope; project APIs currently scope by `owner_user_id`.

## Frontend Boundaries

- API calls live in `website/src/api/`.
- Shared HTTP contract types live in `website/src/types/`.
- Keep ordinary Assistant streaming in the authenticated POST SSE boundary at `website/src/api/project-agent-stream.ts` and `/api/v1/projects/:projectID/agent/conversations/:conversationID/messages/stream`. Stream only truthful backend stages plus provider-supplied reasoning/content; do not synthesize reasoning in the browser or move prompts, tool schemas, provider policy, or generated-source validation out of the backend. Preserve the per-send `client_request_id` on both persisted messages and use that exact ID for post-disconnect reconciliation; prompt-text matching is not safe across tabs or repeated requests.
- Page-level routes live in `website/src/views/`.
- Keep browser Feature DSL capability names in `website/src/cad/feature-dsl-capabilities.ts`; protocol validation must use that registry, and OCCT compiler dispatch must keep its declared coverage equal through `feature-dsl-capabilities.test.ts`. The Go backend owns a separate local registry for validation and provider prompting; parity is enforced by focused tests rather than generated cross-language source.
- `ProjectView` is the thin project route shell: read the route parameter, load project detail, render loading/error states, and pass `useProjectWorkbenchRouteControllers(...)` output into `ProjectWorkbenchComposition`. Keep route-level workbench controller assembly in `useProjectWorkbenchRouteControllers(...)`: it wires History query state, STEP export targets, Assistant enablement, CAD command adapter refs, draft commands, keyboard commands, Inspector derivation, thumbnail publication, and upload/export/controller objects without rendering UI. Keep serialized CAD mutations, revision conflict refresh, and transform autosave in `useCADDocumentCommands(...)`; keep transform/box draft state, local transform draft parsing, autosave scheduling calls, box draft fallback/update/apply wiring, draft translation overlays, and post-delete/transform-sync draft cleanup in `useProjectWorkbenchDraftCommands(...)`; keep Assistant conversations, messages, generation mutations, and retry state in `useProjectAssistantController(...)`; keep saved parametric source loading, local parameter preview overrides, LiteCAD DSL preview mesh caching, route-level selected model/node/artifact state, model/CAD document queries, browser-kernel STEP preview queries, backend preview artifact/blob publication, workbench model tree, preview assets, visible model IDs, and canvas status derivation in `useProjectWorkbenchModelState(...)`; keep selected-model display names, document details, Inspector selection payloads, local transform draft fallback, selected box draft fallback, and selected export/error status derivation in `useProjectWorkbenchInspectorState(...)`; keep project info / STEP export / History open state, CAD conflict-to-History opening, Assistant column visibility/transition/resizing, panel resize handlers, Escape-to-close behavior, and workbench grid/canvas offset derivation in `useProjectWorkbenchShellState(...)`; keep ViewCube/view-orientation state, preview orientation event synchronization, and view rotate/flip/reset command derivation in `useProjectWorkbenchViewControls(...)`; keep Undo/Redo and selected-node Delete/Backspace global keyboard listeners in `useProjectWorkbenchKeyboardCommands(...)`; keep hidden model ID state and visibility toggles in `useProjectWorkbenchVisibilityState(...)`; keep generated artifact save-as-model and saved parametric model parameter mutation/invalidation glue in `useProjectWorkbenchParametricModelCommands(...)`; keep STEP export selection/status orchestration in `useProjectStepExportController(...)`; keep workbench thumbnail snapshot publication and dedupe in `useProjectThumbnailSnapshotController(...)`; keep CAD model upload mutation, error state, and project model refresh in `useProjectModelUploadController(...)`; keep top-level workbench slot composition and cross-controller UI callback wiring in `ProjectWorkbenchComposition`; keep the route-level workbench grid and topbar/main/Assistant column shell in `ProjectWorkbenchLayout`; keep detailed topbar presentation and topbar command wiring in `ProjectTopbar`; keep canvas presentation, canvas status, CAD tool chrome, and view-orientation controls in `ProjectCanvas`; keep sidebar presentation, model tree placement, parametric editor placement, Inspector placement, collapse chrome, and resize handle markup in `ProjectWorkbenchSidebar`. History, STEP export, Assistant, model tree, topbar, canvas, sidebar, and Inspector UI remain controlled components that receive data and callbacks instead of fetching route state themselves.
- Keep the left-panel and Assistant-panel open state and widths in the versioned `useProjectWorkspacePreferences(...)` browser-local boundary. Treat these as non-sensitive presentation preferences, not project data or React Query server state, and retain stored-value validation plus runtime width clamps.
- Reuse the existing React Router, React Query, Tailwind, shadcn/ui component conventions, Lucide icons, Axios, and Three.js patterns.
- UI components must use or compose shadcn/ui primitives unless shadcn/ui has no suitable component for the requirement.
- Do not hard-code backend origins in components; use the Vite proxy and shared `/api/v1` Axios client.

## Product Boundaries

- `docs/openscad-browser-runtime-decision.md` rejects bundling the current GPL-2.0 OpenSCAD WebAssembly candidates into LiteCAD's MIT single-binary distribution. Keep OpenSCAD as a parameter-editable source-draft format; do not enable browser compilation, normal Save as model, or project export unless the decision's license, provenance, sandbox, output-contract, size, and browser gates are all satisfied.
- Current projects include owner-scoped project/source records; schema v4 assembly groups, immutable-revision occurrences, hierarchical suppression, deterministic `point-coincident-v1` translation mates, migration-safe legacy unresolved mate records, and project-local immutable revision-1 subassembly definitions with expanded revision-pinned instance members; reversible database-backed History including all solver-propagated placements plus reusable-definition/instance creation; browser-kernel STEP and LiteCAD DSL preview/export; generated export history; preview and exact OCCT inspection records; section association generations; persisted CAD Agent conversations and parametric artifacts; and versioned recursive `.lcad.json` source-graph editing. LiteCAD Feature DSL covers the capability registry described in `AGENTS.md`, including true symmetric all-eligible-edge chamfer. Projects are still not complete durable B-rep CAD documents, general mechanical constraint systems, live/nested/cross-project reusable subassembly document systems, durable kernel feature graphs, automatic CAD-document section-feature systems, or cross-revision user-selectable metrology systems.
- Current STEP workbench preview and STEP export use the embedded browser CAD kernel worker described in `docs/browser-cad-kernel-roadmap.md`. CAD document schema v4 stores one durable assembly with nested organizational groups; occurrences pin immutable model revisions and independently own name, order, parent group, suppression, and placement inside the existing document revision and History envelope. One source revision may have multiple occurrences. Eligible ordinary leaf groups can be captured as immutable reusable definitions; instantiation creates a tagged group plus ordinary expanded occurrences whose model revision, relative transform, name, suppression, and membership remain pinned. Production preview and export omit occurrences suppressed directly or by any ancestor group, replay box-union geometry in the worker, and apply solver-resolved or instance-pinned occurrence placement in the Three.js scene or exported shape. A `point-coincident-v1` mate preserves the driven occurrence's 3 x 3 transform and solves translation from local anchors plus world offset through an acyclic single-inbound graph; driver edits and Undo/Redo update every affected downstream placement atomically. The default workbench hides position-link management when none exist and exposes existing links only through collapsed advanced management; do not restore raw driver/driven anchor-coordinate authoring without a deliberately approved novice-facing workflow. Schema v3 unresolved records migrate without movement. This is not rotational or general mechanical solving, live-linked/nested reusable documents, or source STEP product-structure preservation. Do not add ad hoc frontend raw CAD loaders outside that kernel plan.
- CAD document edits, occurrence duplicate/update/move/delete commands, model parameter/version transitions, Undo, and Redo are server-authoritative transactions. Require `expected_revision`, return `409 Conflict` for stale callers, and update the materialized document, active model revision, and database History head atomically. Assembly export source reads must use the occurrence-pinned immutable revision source route rather than the model row's current source cache.
- Saved `.lcad.json` graph edits replace one complete validated source document after browser `feature-dsl-preview` succeeds. Keep the parameter schema/value envelope unchanged; require globally unique already-trimmed IDs across top-level features and recursive boolean operands; create one immutable model revision; update occurrence revision bindings; and append one reversible graph-versioned `feature-graph-change` History command with JSON-Pointer-safe node paths, before/after sibling indexes, and added/updated/moved/removed transitions inside the same `expected_revision` transaction. The Inspector graph rail edits one stable recursive node at a time while the advanced complete-source editor handles structural changes. Do not describe this durable source-graph versioning as durable serialized OCCT shape state, cross-revision B-rep topology naming/remapping, sketch constraints, or full B-rep feature history.
- The home and project workbench Three.js surfaces must use project-owned source or derived preview data instead of hard-coded demo geometry.
- Treat AI-driven geometry mutation, CAD tool execution, user-selectable or cross-revision topology measurement semantics, mechanical/rotational assembly constraints beyond `point-coincident-v1`, live/nested/cross-project subassembly documents beyond immutable snapshots, editable B-rep geometry documents, and full STEP B-rep semantics as roadmap work unless the code implements the end-to-end flow. Schema v4 grouping, point-translation solving, project-local immutable reusable snapshots, generated export history, exact aggregate inspection, explicit section association generations, CAD Agent conversations/artifacts, browser-kernel LiteCAD DSL preview/export, immutable model revisions, and recursive source-graph History are implemented. Successful OpenSCAD browser mesh compilation, full prompt-to-geometry mutation, a general mate solver, reusable-definition evolution/deletion or live propagation, automatically regenerating CAD-document section features or section solids, preserved source STEP assembly structure, and cross-model CAD booleans are not.
- AI-generated LiteCAD feature DSL source artifacts have a first end-to-end generated-source path through Assistant draft creation, browser-kernel draft preview before save, browser-kernel preview/export after save, and locally immediate preview updates with debounced revision persistence and stable viewer-scene mesh updates. Do not describe that as AI-driven CAD document mutation, full B-rep generation, or successful OpenSCAD mesh compilation. Do not copy CADAM code; use it only as product-flow reference.
- LiteCAD is not launched yet, so new AI Parametric Assistant phases can prefer clean internal schemas and API contracts over backward-compatible legacy routes or data migrations unless a later requirement explicitly preserves existing sample data.
- Treat general CAD merge/boolean operations as roadmap work unless the code implements the end-to-end flow. A constrained per-model STEP box-union operation, direct per-occurrence STEP export, and selected multi-occurrence STEP compound export are implemented.
- STEP/STP upload metadata extraction is Go-only lightweight source scanning, not geometric B-rep import. Keep full STEP geometry import, preview, edit replay, and export behind the browser CAD kernel worker boundary.
- Normal runtime code must not depend on FreeCAD, `freecadcmd`, or Python-based STEP conversion. New CAD import/edit/export work should stay behind the browser CAD kernel worker boundary and avoid third-party desktop CAD software dependencies.
- When a feature becomes real, update README and remove or rewrite the matching TODO item in the same change.
- Before switching machines or pausing an active CAD semantics branch, refresh `docs/current-work-handoff.md` with the current branch, verification commands, shipped boundary, and recommended next branch.

## Change Checks

- Start code changes with `git status --short`.
- Keep changes small and product-oriented without breaking the single-binary deployment model.
- Run `task check` before committing.
- Run `task test` when behavior, API contracts, database models, auth/session behavior, or UI interactions change.
